# 07. 非機能・セキュリティ要件

## 1. 環境区分

| 環境 | 認証 | データ |
|---|---|---|
| 試作・デモ | 不要 | ダミーデータのみ。実在顧客情報を禁止 |
| 初期本番 | Googleログイン必須 | 実在する在庫・顧客・受注 |

## 2. 認証・アクセス

- 本番は共通Googleアカウントまたは招待済みGoogleアカウントだけが利用できる。
- URLを知っているだけでは本番データを閲覧できない。
- 作業画面と管理画面は表示上分けるが、初期本番では細かな権限制御を行わない。
- 作業担当者は管理者がマスター登録し、操作時に選択する。
- 無効化した作業者も過去履歴には残す。
- 共通アカウントの端末紛失・退職者対応は本番前の未解決事項とする。

## 3. 個人情報

- 顧客、郵便番号、住所、配送先を個人情報として扱う。
- Googleカレンダーへ顧客名・住所を送信しない。
- CSV出力には本番と同じ認証を要求する。
- 試作環境へ実在顧客情報を投入しない。
- 本番の保管期間、削除、アクセス記録の詳細は段階2前に確定する。

## 4. データ完全性

- 重量、予約、出荷の整合性検証をサーバー側でも行う。
- 同一在庫の同時確定時は後続処理を失敗させ、最新値を再表示する。
- 修正前後の値を履歴へ保存する。
- 内部IDと表示IDを分離し、表示ID重複を禁止する。
- カレンダーイベントIDを保存し、再試行で重複予定を作らない。

## 5. 性能・規模

暫定上限を次のとおりとする。

| 項目 | 目安 |
|---|---:|
| 年間受入ロット | 1,000件 |
| 年間コンテナ | 20,000件 |
| 年間受注 | 10,000件 |
| 年間出荷 | 10,000件 |
| 同時利用者 | 10人以下 |
| データ保持 | 7年以上 |

- 一覧を全件表示せず、検索、絞り込み、ページ分割を使用する。
- 通常の登録・画面遷移は安定したネットワーク上で数秒以内を目標とする。
- スマートフォンで重量入力と完了操作が滞らないことを優先する。

## 6. バックアップ・復旧

- 少なくとも日次バックアップを取得する。
- 暫定目標は当日朝の状態まで復旧できることとする。
- 復旧手順、復旧時間、復旧テスト頻度は本番運用前に確定する。
- CSV出力は業務継続・データ移行の補助手段とし、正式バックアップの代替にはしない。

## 7. Googleカレンダー連携

- アプリを正本とする一方向同期とする。
- 共通の農園カレンダーへ予定を登録する。
- 日程変更時はイベントIDを使用して更新する。
- 中止時は削除せず、中止履歴が分かる形で残す。
- 同期失敗時も追熟計画は確定し、自動再試行する。
- 同期失敗件数を管理画面へ表示する。
- カレンダー側の手動変更は次回同期でアプリの値へ戻す。
- イベントには作業種別、品種、等級、重量、必要時の場所、アプリリンクを載せる。

## 8. 対応端末

- 作業画面：主要なスマートフォンブラウザ、縦向き360〜430pxを優先。
- 管理画面：PCブラウザを優先。
- 端末判定は初期表示だけに使用し、ユーザーが画面モードを変更できる。
- ネットワークは安定している前提とし、オフライン同期は行わない。
- 障害時の紙記録を後から実績日時指定で入力できる。

## 9. 初期対象外

- オフライン動作
- QRコード、バーコード、RFID
- 温度センサー連携
- プリンター直接制御
- 個人別Googleアカウントと詳細権限
- 返品、返金、請求、入金
- 加工用・規格外在庫
- 追熟失敗時の再処理
- 本格的な棚卸・在庫調整
- 過去AppSheetデータ移行

## 10. 運用上の注意

- 管理画面の直接修正は、履歴を残すアプリ機能として実装し、データベースを直接編集しない。
- 次工程開始後の訂正方法が確定するまで、該当データの修正を禁止する。
- 本番公開前に、実在顧客情報を使ったアクセス確認とバックアップ復旧試験を行う。
