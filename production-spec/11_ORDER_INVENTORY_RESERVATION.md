# 11. 在庫選択から始める受注と受注時予約

状態：受注入力前の在庫選択と受注登録時の確保はユーザー合意済み。以下の整合性・移行要件を実装時の設計条件とする。DB・API・画面を実装済み。ローカル自動検証済み。担当レビュー・配備後の現場確認は未実施。
追跡Issue：[S2-10 #109](https://github.com/Re-Ochuns/Kiwi_peoducts/issues/109)。
変更区分：L4。実装PRではFrontend・Backend・DB/CIの影響レビューを行う。

## 合意した操作フロー

1. 受注入力を始める前に、受注画面で利用可能な冷蔵在庫を確認する。
2. 品種・等級で絞り込み、使用するコンテナを選ぶ。
3. 「この在庫で受注登録」から顧客・配送先・注文日・出荷予定日・注文量・各コンテナの使用量を入力する。
4. 確認画面で受注内容と予約対象・予約量を確認し、受注を確定する。
5. 受注と予約を同一トランザクションで保存する。
6. 追熟計画では対象受注の予約済み在庫を引き継ぐ。

一覧閲覧、候補選択、入力中には在庫を確保しない。確定時に利用可能量を再検証する。選択画面へ戻っても、同一操作中の顧客・配送先・日付など入力済み内容を保持する。

## 画面の要件

- 受注画面に「受注用在庫」と既存受注一覧を設け、受注入力フォームを開かずに在庫を確認できる。
- 品種・等級、コンテナID、産地、選果日、保管場所、現在量、予約済み量、利用可能量を表示する。
- 検索・絞り込み・ページングを用い、対象全件をクライアントへ読み込まない。
- 一受注の品種・等級は既存仕様を維持する。同一品種・等級の複数コンテナを選択できる。
- 0.01kg単位の使用量、合計、選択コンテナごとの残り利用可能量を表示する。
- 注文量と予約量の合計を一致させて確定する。在庫不足の場合、顧客入力を失わず在庫の再選択へ戻せる。
- 受注詳細に元コンテナ、予約量、未計画分、追熟計画へ引き継いだ分を表示する。
- 追熟計画画面では「この受注の予約在庫」と「未予約の利用可能在庫」を区別する。他受注の予約を使用できない。
- 下書き保存を残す場合は未予約であることを表示し、確定済み受注と区別する。通常の新規受注の完了操作は「受注・在庫予約を確定」とする。
- 管理PC幅900px・1280px、作業者の追熟計画幅360〜430pxで表示と予約引き継ぎを確認する。

## データとトランザクション

- 追熟ロット未作成でも、受注・元コンテナ・予約重量を関連付けて保存できる構造とする。
- 予約の所有者（受注、または受注のない予備計画）と、使用予定の追熟計画を区別する。
- 予約量 = 未計画の受注予約量 + 計画に関連付け済みの予約量。引き継ぎ前後で同じ重量を二重計上しない。
- 利用可能量 = 現在量 − 全有効予約量。受注画面・在庫一覧・追熟計画・CSVで同じ定義を用いる。
- 確定時に対象コンテナを一貫した順序でロックし、状態・品種・等級・利用可能量・予約合計をサーバー側で検証する。
- 受注だけ、または予約だけが残る部分成功を許可しない。タイムアウト後の再送も同じ冪等性キーで重複を防ぐ。
- 作成・調整・解放・計画引き継ぎの履歴に、対象受注・元在庫・重量・操作者・理由・相関IDを残す。
- クライアントのテーブル直接更新は禁止。認証・既存の管理者権限・RLSを維持する。

## 追熟計画・変更・取消との整合

- 受注用の追熟計画は、その受注が持つ予約を使用する。追加予約として重ねて確保しない。
- 一受注の部分計画、複数受注と予備を含む計画の既存機能を維持し、元コンテナのどの予約がどの受注に属するか追跡可能にする。
- 予備計画は受注に属さない利用可能量から予約する。
- 作業開始前に追熟計画を取り消しても、有効な受注の予約は解放せず「未計画」へ戻す。予備分は利用可能在庫へ戻す。
- 作業開始前の受注取消では、その受注の予約だけを解放する。共有計画内の他受注・予備の予約を巻き込まない。
- 受注変更時は予約対象・予約量も同一トランザクションで調整する。増量時の不足では変更全体を取り消す。
- 計画に影響する変更は既存の要再確認処理と整合させる。作業開始後の変更・取消は既存の制約を緩和しない。
- 注入時は予約を使用済みにし、元在庫減算・追熟コンテナ生成と整合させる。

## 既存データ・配備

- 既存受注へ在庫を自動割当しない。対応関係を推測して新規予約を作らない。
- 既存の有効予約は移行で増減させない。受注所有分と予備分を区別できない既存の複合計画は、所有者なしの旧予約として維持する。旧受注の取消は所有者付き予約へ影響させない。
- 過去の使用済み・解放済み予約、出荷・取消・監査履歴を維持する。
- 後方互換migration → API → 画面の順に配備し、旧アプリへの切り戻し時にも二重予約を防げることを確認する。
- 旧経路から確定して予約なしの新規受注が作成できる期間を設けない。切替方式を配備手順へ記載する。

## 受入条件

- 在庫確認 → コンテナ選択 → 受注入力 → 確定時予約 → 追熟計画引き継ぎ → 注入までを同じテストデータで通せる。
- 確定前は利用可能量が変わらず、確定後は予約量だけ減る。現在重量は出庫まで減らない。
- 同じ在庫を同時に確定しても過剰予約・部分成功・重複が発生しない。
- 注文量と予約合計の不一致、品種・等級不一致、冷蔵以外の対象は拒否する。
- 受注の変更・取消、計画の変更・取消、部分計画、複合計画で予約の所有者と残量が整合する。
- 在庫一覧とCSVの予約量・利用可能量が一致する。
- 既存データを含むDBテスト、Repository/APIテスト、画面テスト、Staging正常系を確認する。

実装契約・エラー・切替手順は[受注時予約RPC](../contracts/rpc/order_inventory_reservation.md)を参照する。
