# 02. MOCKとの差分一覧

| 領域 | 現行MOCK | 本番要件 | 影響 |
|---|---|---|---|
| 利用者 | 単一作業者を想定 | 作業者向けスマホ画面と管理者向けPC画面 | ナビゲーションと画面構成を分離 |
| 認証 | なし | 本番は共通または招待制Googleログイン | 顧客情報保護、セッション管理が必要 |
| 受入区分 | 収穫中心、仕入れはチェック | 収穫と仕入れで条件付き項目を切替 | 仕入先マスター、区分別入力が必要 |
| 受入単位 | 樹体単位重量 | 受入ロット総重量＋コンテナ数 | ロットモデルを拡張 |
| 選果前 | 収穫済み | 冷蔵中の選果待ち | 工程状態を追加 |
| 選果期限 | 2日固定 | マスター設定、初期30日 | 年度・収穫月・品種ルールが必要 |
| 選果入力 | 等級重量＋コンテナ数 | コンテナを追加し個別実測重量を入力 | UIと重量計算を変更 |
| コンテナ生成 | 個数から重量を自動配分 | 選果後から個別IDを発行 | コンテナエンティティが必須 |
| ロス | 差分を自動計算 | 同様。ただし警告基準は未決 | 将来の警告設定を考慮 |
| ラベル | 印刷成功を模擬 | PDF印刷、部分印刷、再印刷、手書き対応 | 印刷状態と履歴が必要 |
| 冷蔵保管 | 一つの工程状態 | 選果待ちと選果後在庫を区別 | 工程状態と期限を再設計 |
| 追熟契機 | 在庫から作業者が開始 | 作業者または管理者が受注・予備から追熟計画を作成 | 受注、計画、割当、予約が必要 |
| 追熟期間 | 固定3日＋7日 | 年度・収穫月・品種マスター | マスターの版管理が必要 |
| 追熟状態 | 追熟→寝かせ→出荷可能 | 計画、予約、現物状態、確認タスクを分離 | 状態モデルを全面変更 |
| 追熟場所 | なし | 場所マスターから選択 | 場所・移動履歴が必要 |
| 予備 | なし | 管理者が量を指定し、後から受注へ振替 | 予備割当が必要 |
| 受注 | 対象外 | 顧客、配送先、品種、等級、kg、状態 | 個人情報と注文状態を管理 |
| 出荷 | 表示のみ | 部分出荷、在庫減算、取消 | 出荷実績と重量イベントが必要 |
| 期限切れ | サンプル表示 | 賞味期限で自動出荷不可、関連計画を要再確認 | バッチ処理または定期判定が必要 |
| ToDo | 要確認件数 | 当日・期限超過・今後の作業 | タスクエンティティが必要 |
| カレンダー | なし | Googleカレンダーへ一方向同期 | 外部API、再試行、イベントIDが必要 |
| 修正 | メモリ上の操作のみ | 修正前後を履歴保存 | 永続化と訂正履歴が必要 |
| データ | 再読込で初期化 | 永続DB、日次バックアップ | 運用・復旧要件が必要 |
| ID | 親IDを含む長い枝番 | 年度別の短い表示ID＋内部ID | 二重ID管理が必要 |
| 規模 | デモ数件 | 年間最大2万コンテナ目安 | 検索、ページ分割が必要 |

## 本番化で最も大きい変更

1. 追熟を単純な状態遷移ではなく、受注から逆算した追熟計画として扱う。
2. 在庫の合計重量だけでなく、選果後コンテナごとの重量・予約・残量を保持する。
3. 計画状態、予約状態、現物状態、作業タスクを分離する。
4. 顧客情報を扱うため、試作版と本番版のアクセス条件を分ける。
5. 出荷実績によって在庫を減算し、システム在庫を閉じる。

## PoC検証で確定した画面方針

- 「追熟」を正式な画面・状態・データ名称として使用し、旧称の「成熟」は使用しない。
- 作業者向けスマートフォン画面から追熟計画を作成できるようにする。
- スマートフォン画面に固定の下部タブを設けない。工程への入口は作業者ホームの作業ボタンへ集約する。
- 選果入力では等級を切り替え、選択中の等級に属するコンテナだけを表示する。
- 選果画面下部の固定領域は、選果後合計、ロス、確認操作だけを表示するコンパクトな領域とする。
- 管理ホームは件数カードを主役にせず、期限超過、在庫・予約不足、外部連携失敗を優先順に表示する。
- 同じ形のカードを多用せず、反復情報は一覧または表で表示する。
