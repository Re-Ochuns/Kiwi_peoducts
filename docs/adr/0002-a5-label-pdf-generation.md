# ADR-0002 A5ラベルPDFはサーバーで生成する

## 状態

承認待ち

## 対象Issue

- FND-07: #8
- 後続: S1-08 #17、S1-09 #18

## 背景

初期本番では、選果後および追熟開始時に日本語A5ラベルPDFを生成し、Flutter Webからブラウザ印刷する。再印刷可能で、生成・印刷状態を監査できる必要がある。バーコード、QRコード、プリンター直接制御は初期対象外である。

## 決定

PDFはSupabase Edge Functionで一元生成し、Flutter Webは認証済みPDFの表示、ダウンロード、ブラウザ印刷を担当する。PDF生成失敗は業務データの確定トランザクションから分離し、同じ入力とレイアウト版から同じ内容を再生成できるようにする。

この決定は、フロント、バックエンド、DB・CI、要件責任者の承認と、対象プリンターでの実機試験後に「承認済み」とする。

## 理由

| 観点 | Flutter側生成 | サーバー側生成 |
|---|---|---|
| レイアウト統一 | 配布中クライアントの版に依存する | レイアウト版を一元管理できる |
| 再生成 | 生成時の端末状態に依存する | 保存入力から再現しやすい |
| 監査 | クライアント処理と履歴の関連付けが必要 | 生成要求・結果・版を記録しやすい |
| 端末負荷 | 端末でフォント読込と生成を行う | Edge Functionへ集約できる |
| 印刷 | ブラウザ印刷が必要 | 生成後は同じくブラウザ印刷を使う |
| 障害時 | 端末別の切り分けが必要 | 生成ログと再試行を一元化できる |

Flutterの`pdf`パッケージはTrueTypeフォントを利用したPDF生成とWebでの保存が可能であり、技術的な代替案として成立する。ただし、初期構成でPDF生成をEdge Functionの責務としたADR-0001、再現性、監査性を優先する。

## 試作結果

- A5縦1ページ、148 x 210 mmで生成できた。
- Noto Sans JPをサブセットとしてPDFへ埋め込み、日本語を抽出・描画できた。
- 10 mmの安全余白内へ、選果後ラベルの必須項目を配置できた。
- コンテナIDと重量を最優先で大きく表示できた。
- 印刷倍率確認用に100 mmの確認線を試作だけへ配置した。
- バーコードとQRコードは要件どおり配置していない。

試作はレイアウトとフォント埋め込みの検証用であり、Python/ReportLabを本番実装として採用する決定ではない。S1-08ではDeno互換の生成ライブラリを選び、同じ入力項目、ページ寸法、安全余白、優先順位を再現する。

## 制約

- 使用したNoto Sans JPの元フォントは約9.1 MBである。
- Supabase Edge Functionは、ローカルCLIでのバンドル上限が20 MB、サーバー側バンドル上限が5 MBである。現状のフォントはサーバー側バンドルへ収まらない。
- S1-08ではローカルCLIバンドル、静的フォントの軽量化、実行時取得のいずれかを計測し、CPU時間とメモリ使用量を確認する。
- ブラウザ印刷では用紙A5、倍率100%または「実際のサイズ」を指定し、ブラウザ・OS・プリンタードライバーによる追加縮小を避ける。
- 実機による印字可能領域、給紙方向、ずれ、耐候性は未確認である。

## 手書きフォールバック

PDF生成または印刷に失敗した場合は、画面にコンテナID、産地・区画、品種、等級、正味重量、選果日または追熟予定、担当者を表示し、同じ項目をA5用紙へ手書きする。利用者が「手書き対応」を明示的に確定した時点で対応済みとし、対象、実行者、日時を履歴へ残す。

## 実機確認後に確定する項目

- 採用プリンター機種と対象ブラウザ
- 印字可能領域と許容ずれ
- 一部印刷時の再印刷単位
- 用紙方向と給紙手順
- 100 mm確認線の実測値
