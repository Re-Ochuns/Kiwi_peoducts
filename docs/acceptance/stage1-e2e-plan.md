# 段階1 E2Eシナリオと受入基準

## 1. 目的と範囲

収穫・仕入れ受入、選果、ラベル対応、冷蔵在庫、マスター、CSV出力を、
作業者のスマートフォンと管理者のPCを使う実運用順序で確認する。
LocalとStagingではダミーデータのみを使用し、実在顧客情報を投入しない。

自動テストは回帰検出の証跡、Stagingと実機の操作は業務受入の証跡とする。
どちらか一方だけでは段階1を受け入れない。

## 2. 役割と環境

| 役割 | 主端末 | 必須確認 |
|---|---|---|
| 作業者 | 360px、390px、430pxのスマートフォン | 受入、選果、ラベル、在庫参照、通信復旧 |
| 管理者 | 1280px以上のPC | マスター、在庫詳細、履歴、CSV、競合後の確認 |
| 現場確認者 | 実際に利用する端末とプリンター | 手順書だけで完遂、可読性、紙フォールバック |
| 記録担当 | PC | 証跡、所要時間、発見事項、判定の記録 |

Stagingのブラウザ、OS、端末名、アプリSHA、実施者、開始・終了時刻を記録する。
複数端末試験では同じStaging環境を同時に参照する。

## 3. テストデータ

- 自園収穫: ヘイワード、第一圃場A区画、樹体A、48.25kg、4コンテナ。
- 仕入れ: 香緑、仕入先A、仕入先管理ID SUP-001、32.40kg、3コンテナ。
- 選果結果: M 10.25kgと9.80kg、L 8.10kg。残りをロスとする。
- 作業者Aは有効、作業者Bは無効。管理者Aは履歴閲覧可能とする。
- 一意な実施識別子を表示ID検索用メモへ残し、他の試験データと混在させない。

## 4. 業務シナリオ

| ID | シナリオ | 操作と期待結果 | 合格基準 | 証跡 |
|---|---|---|---|---|
| E2E-01 | 自園収穫から在庫 | 作業者が自園収穫を登録し、全量を選果し、各ラベル対応後、管理者が在庫を開く | 受入重量、選果合計、ロス、全コンテナの正味重量と一意な表示IDが一致する | 受入・選果・ラベル・在庫の各画面、表示ID一覧 |
| E2E-02 | 仕入れから在庫 | 仕入先と管理IDを指定し、樹体を入力せず登録後、選果・ラベル対応する | 樹体が要求されず、発生元が仕入れとして在庫詳細まで追跡できる | 入力確認、完了、在庫詳細 |
| E2E-03 | 重量超過拒否 | 選果後合計を元重量より0.01kg大きく入力して確定する | 確定されず理由が表示され、DBにコンテナを生成しない | エラー画面、対象ロットとコンテナ件数 |
| E2E-04 | 印刷正常系 | A5 PDFを開き、1枚印刷後に利用者が成功を明示する | 明示確認前は未印刷、確認後だけ印刷枚数と履歴が増える | PDF、印刷物、状態、履歴 |
| E2E-05 | 手書きフォールバック | 印刷不能を想定し、必須項目を見ながら手書き対応を確定する | 手書き対応済みとなり、誰がいつ対応したか履歴に残る | 手書きラベル、完了画面、履歴 |
| E2E-06 | 再印刷 | 印刷済みラベルへ理由を入力して再印刷する | 理由なしでは実行不可。理由、担当者、再印刷回数が履歴に残る | 再印刷画面、印刷物、履歴 |
| E2E-07 | 複数端末参照 | スマートフォンで作成した在庫をPCで検索し、続けて別スマートフォンで参照する | 同じ表示ID、重量、状態、場所を表示し、再読込後も一致する | 3画面の同一ID |
| E2E-08 | ロール制御 | 作業者と管理者で同じ在庫を開き、無効作業者を新規操作で選択する | 作業者へ管理履歴を開示せず、管理者は閲覧可能。無効作業者は選択不可だが過去履歴には残る | 両ロールの画面、過去履歴 |
| E2E-09 | CSV出力 | 在庫、マスター、変更履歴を絞り込み、CSVを出力する | 認証が必要で、現在の条件だけをUTF-8の所定列で出力する | 条件画面、CSV、件数照合 |

E2E-09は依存Issue #19が完了するまでBlockedとする。

## 5. 障害・競合シナリオ

| ID | 条件 | 操作 | 合格基準 |
|---|---|---|---|
| RES-01 | 受入確定直後に通信を遮断 | 同じ内容で再試行する | 同じ冪等性キーを使用し、受入ロットを重複作成しない |
| RES-02 | 選果確定直後に応答を遮断 | 記録結果を再確認する | コンテナと表示IDを重複作成せず、確定結果を取得できる |
| RES-03 | PDF取得またはポップアップ失敗 | 再試行または中断する | 印刷済みへ変更しない |
| RES-04 | 印刷記録直後に応答を遮断 | 記録結果だけを再確認する | PDFを再表示せず、印刷枚数を二重加算しない |
| CON-01 | 2端末で同じ受入ロットを開く | 同時に選果確定する | 一方だけ成功し、他方は競合表示後に最新状態を再読込する |
| CON-02 | 2端末で同じラベルを開く | 印刷済みまたは手書きを同時確定する | 古い状態の確定を拒否し、履歴と枚数が一貫する |
| AUTH-01 | 未認証・無効ユーザー | URLを直接開く | 業務データを表示せず、ログインまたは利用不可画面になる |

通信遮断にはブラウザ開発者ツールのOfflineを使用する。
確定ボタン押下前から遮断せず、「サーバー処理済みだが応答不明」を再現できるプロキシまたは試験手順を用意する。

## 6. 性能シナリオ

| ID | データ量・負荷 | 測定 | 合格基準 |
|---|---|---|---|
| PERF-01 | 受入1,000件、コンテナ20,000件 | 在庫初期表示、ID検索、状態絞り込み、次ページ | 各操作のp95が3秒以内、全件DOM表示を行わない |
| PERF-02 | 同時利用10セッション | 受入参照、在庫検索、ラベル対象取得 | エラー率1%未満、整合性違反0件 |
| PERF-03 | 1受入から最大想定コンテナ数を選果 | 入力応答、確認、確定 | 入力が目視で停止せず、確定が10秒以内 |
| PERF-04 | 変更履歴7年相当 | 在庫詳細と履歴表示 | p95が3秒以内、ページまたは上限で制御される |

p95は同一条件を最低20回実行して算出する。初回ウォームアップは集計から除外する。
暫定基準を超えた場合は計測値と利用影響を記録し、責任者が受入可否を判断する。

## 7. 実機印刷と手書き復旧

`docs/printing/a5-label-verification.md`の手順に従い、A5縦、倍率100%、
ブラウザのヘッダー・フッターなしで実機印刷する。

追加で次を確認する。

1. 100mm確認線の実測値、四辺の欠け、文字化け、にじみ、給紙方向を記録する。
2. 3m離れてコンテナIDと重量を読み取る。
3. 印刷不能時に手書きラベルへ切り替え、作業を継続する。
4. 復旧後は手書き済みを通常印刷済みに上書きせず、必要なら理由付き再印刷として記録する。
5. 実物コンテナとシステムの表示ID、品種、等級、重量を再照合する。

## 8. 発見事項の分類

| 分類 | 定義 | 例 |
|---|---|---|
| 不具合 | 確定済み要件を満たさない | 重量不一致、履歴欠落、操作不能 |
| 仕様変更 | 要件自体を変える必要がある | 必須項目、状態遷移、確定手順の変更 |
| 運用課題 | システム外の手順・設備で解決する | 用紙保管、プリンター担当、通信障害時の保管場所 |

各発見事項に重大度、再現手順、証跡、暫定回避策、責任者、対応期限を付ける。
P0/P1は解消または受入責任者の明示判断までGoにしない。

## 9. 自動検証

`scripts/run_stage1_acceptance.sh`は次をまとめて実行する。

- 固定ツールバージョン、format、analyze、Unit・Widgetテスト。
- UTC環境のGolden、Flutter Web release build。
- migration再構築、DB lint、RLS・RPC・競合pgTAP。
- A5 PDFの寸法、埋め込みフォント、必須文字列、安全余白検査。

自動検証の成功は実機印刷、Staging、複数端末、現場確認の代替ではない。
