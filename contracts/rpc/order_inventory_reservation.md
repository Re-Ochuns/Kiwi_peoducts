# RPC契約: 受注時の在庫予約

- 対象Issue: #109 / 版: 2
- `20260914000300_add_order_inventory_reservations.sql` で追加。
- 業務正本: [受注時予約](../../production-spec/11_ORDER_INVENTORY_RESERVATION.md)

## 入力・結果

`order_register` と `order_update` の `input.reservations` に、`container_id`（UUID）と `reserved_weight_kg`（正の0.01kg単位）を持つ配列を渡す。1〜100件、コンテナ重複不可。同一品種・等級で、合計は `ordered_weight_kg` と一致する。

指定時は受注保存・予約確保・受注確定を同じトランザクションで行い、`confirmed` の受注を返す。登録直後のversionは2。更新の `expected_version` と理由、共通RPC封筒・認証・管理者権限・冪等性は従来通り。

予約なしの旧クライアントによる新規登録は下書きとなるが、その後の確定は拒否する。予約に対応した画面で編集・確定する。移行前から存在する受注（`inventory_first=false`）の振る舞いは維持する。既存の計画割当がある旧受注を新方式へ変更する場合、計画を先に取り消す。

`order_get` は `reservations` を追加して返す。有効または使用済みの所有予約行に `display_id` を付与。`ripening_lot_id=null` は未計画。計画のある行は計画済み。元の受注レスポンス項目を維持する。

## 参照API

- `order_inventory_available(search_value='', variety_value=null, grade_value=null, offset_value=0, order_value=null)` → JSON行の集合。1回最大51件（50件表示と次ページ判定）。コンテナIDで検索し、品種・等級で絞る。現在量・予約量・利用可能量・当該受注の有効予約量・品種/等級名・産地・選果日・保管場所を返す。`order_value` は編集時の既存予約の表示用であり、他受注の予約を利用可能にしない。
- `ripening_order_inventory()` → 未計画の有効受注予約をコンテナ・受注単位に集計した `{container_id, order_id, weight_kg}` の集合。
- いずれもsecurity invoker。既存RLSに従い、匿名実行は禁止。有効利用者が閲覧する。

## 排他制御・副作用

受注と計画は既存のアドバイザリロック `(53,0)` を共有。対象コンテナをロックし、確定時の利用可能量を再計算する。`inventory_reservations.owner_order_id` が予約所有者、nullableな `ripening_lot_id` が使用計画。予約の計画への移動では現在量・予約総量を変更しない。部分引き継ぎでは行を分割する。

計画登録/更新の内訳に新方式の受注が含まれる場合、指定した元コンテナにあるその受注の予約を使用する。予備・移行前受注の分だけ未予約量から新規予約する。計画取消は所有予約を未計画に戻す。受注取消は所有予約だけを解除し、共有計画の他受注・予備分を維持して計画を要再確認にする。旧受注の取消も所有者付き予約を解除しない。

受注編集ではコンテナごとの計画済み量以上を維持する。計画済み在庫の変更・削除は先に計画を見直す。注入時は同一コンテナの複数所有予約をまとめ、元在庫イベントを1件作成する。予約の作成・分割・移動・解放には操作者・理由・相関ID付き履歴を残す。

## 業務エラー

- `ORDER_RESERVATION_REQUIRED`: 新方式の受注の予約が未指定。画面を再読み込みし、在庫を選択して確定する。
- `ORDER_RESERVATION_MISMATCH`: 予約合計と注文量の不一致。
- `ORDER_RESERVATION_PLANNED`: 計画済み量を下回る変更、計画済み元在庫の削除、計画割当のある旧受注の方式変更。
- `ORDER_RESERVATION_UNAVAILABLE`: 計画内訳に対応する所有予約が指定元在庫に足りない。
- `INVENTORY_UNAVAILABLE`: 品種・等級・冷蔵状態・利用可能量の不一致。
- `CONFLICT_STALE`: version不一致、変更・取消が許可されない作業開始後の状態。

いずれも共通エラー封筒を返し、部分更新を残さない。冪等性キーは内容を変えず再送する。業務エラー後に入力を修正した場合は新しいキーを使用する。

## 移行・配備

既存行は所有者なしの旧予約として数量・履歴を保持し、推測による受注への割当を行わない。マイグレーションを先に配備してから新アプリを公開する。旧アプリは既存受注を扱えるが、新規受注の確定には再読み込みが必要。切り戻しでも新方式受注の旧経路からの無予約確定は拒否し続ける。新DBを旧スキーマへ戻すマイグレーションは行わない。

追熟マスターの収穫年度・月の明示設定、注入後のラベル対応など、従来の追熟工程の前提は変更しない。
